**一、做好AI coding需要什么**

**1. Set Foundation——建立概念地图，再精准提问**

对陌生的业务和技术，先建立「领域内」的「符号」体系。不是要变成专家，而是能和 AI 正确对话。

**实践线索**：

项目启动前，先调研 OpenClaw 技术体系和 Telegram 插件源码，目的不是读懂每一行代码，而是搞清楚「有哪些机制存在」——插件通过什么方式注册、框架怎么做会话隔离、文件收发各走什么路径。有了这张粗粒度的概念地图，才能开口就说到点上，而不是让 AI 先帮你猜需求在框架里对应什么，避免鸡同鸭讲。

  

**2. Design First——先设计，再实现**

大的需求或模块，先设计，Review 没问题，再实现。不要直接开始 coding。

  

**三个层次的设计**：

  

- **需求实现规划**：基于需求，划定各模块的边界和职责，明确「谁做什么」，确认整体方案可行再往下走  
    
- **整体设计文档**：定义 API 的数量、参数、响应格式、状态码、认证方式、关键设计决策（为什么这样设计），与 AI 多轮讨论后 Review 定稿  
    
- **模块详细文档**：每个模块/接口独立成文，明确请求/响应字段、业务状态码、Sequence Diagram（完整调用链路）、边界情况和设计说明——这是给 AI 实现时的精确输入，不是模糊描述  
    

**实践线索**：

  

Bot API 先完成整体设计文档（im-design-v1.md），包含接口列表全貌、认证方式、消息状态、核心设计决策（Long Polling vs WebSocket、文件上传下载安全处理），经过人工 Review 和与 AI 多轮讨论后定稿。

  

整体文档确认后，再为每个接口单独出文档。以 getUpdates 为例：文档包含完整的请求/响应字段表、offset 语义说明、双层消息检测机制（内存 → Redis 100ms 轮询）、消息过滤规则、Sequence Diagram 覆盖三条执行路径（内存命中 / Redis 唤醒 / 超时返回）。按照「需求实现规划 → 整体设计文档 → 模块详细文档」三层递进，实现时 AI 拿着这份文档写代码，不用再对关键决策做假设。

  

**3. Set Evaluation Rule——设立标准，知道什么是对的**

AI 生成代码的质量上限，由你的评估标准决定。没有标准，AI 只能以「能跑起来」为目标。

  

三个维度：

  

- **结果正确**：可编译、逻辑正确、测试通过  
    
- **路径正确**：有成熟最佳实践的部分，写出 idiomatic 的代码——符合语言惯用法、框架约定、项目规范，AI 按套路走即可  
    
- **taste**：没有标准答案的部分，靠个人品味判断——命名是否直觉、抽象是否合适、职责是否内聚。这部分 AI 给不了你答案，只有你自己知道「对的感觉」是什么  
    

**实践线索**：

  

- **结果正确**：CLAUDE.md 约束 AI「修复前必须先分析根因，经我确认后才能改动代码；不要自行打包」——每次改动都有明确预期，测试是验收手段，约束是防止 AI 乱改导致结果不可预测。  
    
- **路径正确**：CLAUDE.md 里写明框架资源路径（openclaw 源码位置、插件日志路径、时区说明），让 AI 在调研时找到正确的参考对象；设计文档里的「设计决策」表格（im-design-v1.md）把「为什么这样选」记录下来，避免 AI 在实现时偏离已确认的方案。  
    
- **taste**：最难书面化的部分。这个项目里体现在两处：一是 Bot API 设计阶段把接口压缩到恰好 7 个：editMessage 并入 sendMessage（有无 message_id 区分新建/覆盖），sendCustom 并入 sendMessage（type: custom），deleteMessage 直接不设计（用 status: cancelled 覆盖代替删除）——接口该合还是该拆，没有标准答案，靠的是对「这个职责该不该独立」的直觉判断；二是路径提取逻辑积累了技术债后，主动安排一次重构而不是让 AI 继续堆代码——「何时该整理」这个判断，没有最佳实践可以参考，完全靠 taste。  
    

**4. Trade-off——在多个方案中做权衡**

用 AI 做事，很快会遇到「多个方案都能实现」的情况。在决定方向的重要选择面前，别让 AI 替你做决定。

  

**实践线索**：

  

- **消息接收协议**：Long Polling vs WebSocket → 选 Long Polling，因为「游标续接天然幂等，断线即新请求，不漏消息；比 WebSocket 实现简单」  
    
- **流式消息方案**：增量 diff vs 全量快照 → 选全量替换，参考 Telegram editMessageText 方案：「客户端本地做打字机动画，服务端推全量消息快照」  
    
- **消息处理并发**：串行 vs 无限并行 → 选 Semaphore 限流（每 chat_id 最多 20 并发），「防止一个对话无限堆积 AI 请求」  
    

**5. Redirect——发现偏差，立刻纠正**

AI 会自由发挥，尤其在问题描述模糊时；上下文过长时，早期约束容易被忽略，判断质量也会下降。发现它方向错了要立刻打断，避免浪费时间和 Token。

  

**实践线索**：两类典型的偏差场景

  

- **跑偏方向**：让 AI 修复一个明确的 bug，它却跑去翻完全无关的其他项目目录寻找源码，越走越远。根因是问题描述范围没有限定，AI 自行扩大了搜索范围。发现后立刻打断，明确告知「只看这个插件目录，不要跨项目」，才回到正轨。  
    
- **脱离现实**：AI 尝试在本地环境查找 OpenClaw 配置文件和插件日志来辅助调试，但本地根本没有安装 OpenClaw。它在一个不存在的环境里兜圈子。这类偏差靠 CLAUDE.md 里的资源约束提前堵住：明确写明「忽略本地安装的 openclaw」「插件日志在 /tmp/baidu-doctorclaw.log」，让 AI 知道该去哪里、不该去哪里。  
    

  

**二、实践技巧**

**技巧一：Sketch Over Random Talk——打草稿与 AI 协作完善，优于直接对话**

稍微复杂的任务，先打草稿整理思路和约束，再和 AI 协作完善成文档，效果远好于直接开口对话。直接对话容易遗漏细节、逻辑混乱，AI 也会见缝插针地加入自己的理解自由发挥。

  

实现并发调度前，直接开口说「帮我做并发处理」，AI 大概率会立刻给一个方案开始写代码——但「同 chat_id 串行、不同 chat_id 并行」的策略是什么，Semaphore 上限怎么定，这些决策会被 AI 悄悄假设掉，等实现完才发现方向不对。

  

先打草稿明确思路和核心约束：把并发策略、并发限流方案、边界情况一一写清楚，自己在动手前想清楚，AI 拿到更多细节再实现，不需要做假设。

  

打草稿、写文档本身也可以和 AI 协作完成：把你的想法、约束、已知边界告诉 AI，让它帮你起草结构、补全细节、提出遗漏的问题。但主导权在你——AI 负责帮你把思路写清楚，不是替你做决策。

  

**技巧二：Context Relay——跨会话用文档传递上下文**

**调研 → 设计 → 实现**不在同一个会话里完成，用文档作为阶段间的上下文桥梁。

  

调研阶段

  → 形成调研文档（channel-telegram.md）

设计阶段（新会话）

  → 基于调研文档，生成设计文档（im-design-v1.md + im-channel插件-design-v1.md）

实现阶段（新会话，每个子模块一个会话）

  → 基于设计文档，生成实现计划（plans/*.md）

  → 基于实现计划，逐步执行

**为什么要拆会话**：上下文过长会导致 AI 效果下降，早期信息被「遗忘」，关键约束被忽略。文档是比「AI 记忆」更可靠的上下文载体。

  

**技巧三：Plan First——计划先于执行，让 AI 先亮底牌**

不要直接让 AI 开始写代码。先让它把「打算怎么做」说出来，双方对齐后再执行。

  

两种交互方式：

  

**方式一：你主动追问（人主导）**

  

AI 出计划草稿，你针对可疑的决策点主动追问：

  

- 「你选了 X 方案，为什么不用 Y？」  
    
- 「如果出现 Z 情况怎么处理？」  
    

适合你对领域有一定判断，能识别出 AI 方案里的隐患。

  

**方式二：要求 AI 主动提问（AI 暴露决策点）**

  

在 prompt 里加指令：「遇到有多个可选方案的设计点，不要自己决定，先列出选项并说明，等我确认再继续。」

  

这样 AI 会把隐性假设主动浮出水面，引导它在关键点上问你，而不是悄悄做选择。适合你对某个领域不够熟悉、不知道该问什么的场景。

  

**技巧四：Provide Just Right Context——主动为 AI 提供高质量上下文**

AI 的输出质量，很大程度上取决于你给它的上下文质量。「提供上下文」不是简单地粘贴代码，而是根据问题类型，选择最有价值的信息。

  

**四类高价值上下文**：

  

**① 系统调用 Trace / 调用链**

  

适用于理解框架内部行为、排查调用路径问题。同时能让 AI 快速理解服务调用链路，建立系统认知。

  

**② 关键日志（含完整错误栈）**

  

适用于运行时异常场景。提供日志时，要包含完整的错误栈，不要截断；要标注时区和时间戳；要把问题发生前后的上下文日志一并提供，不只是报错那一行。

  

**③ 问题现象的准确描述**

  

- **差的描述**：「发送文件不生效」  
    
- **好的描述**：「发送包含 MEDIA: /tmp/a.png 的文本消息，预期触发模式1（文件消息处理路径）走 sendFile，实际走了普通文本发送路径」  
    

准确描述能让 AI 直接定位问题域，不需要先花时间理解「什么叫不生效」。

  

**④ 接口的输入输出数据 + 关键字段含义**

  

适用于接口联调、协议对接、数据格式问题。实际联调时遇到问题，直接把请求体和响应体粘贴给 AI，比描述「发送失败了」有效 10 倍。

  

**原因在于**：AI 是根据「当前会话的信息」工作，而不是根据「客观存在的信息」工作。你不说，它就不知道。主动管理你给 AI 的上下文，是使用 AI 最核心技能之一。

  

**技巧五：Decompose & Verify——拆 Task，定义验收，选择节奏**

把大问题分解成多个有明确边界的子任务，为每个 Task 定义验收标准。

  

**为什么要拆**：Task 太大是 AI Coding 最常见的失控来源。粒度太粗，AI 会在内部做一堆没经过你确认的决策；出错后影响范围大，难以定位。Task 要小到「一次可以被验证」。

  

**验收标准是核心**：不只是质量保障，更是你和 AI 之间的「共识契约」。先定义期望行为，再让 AI 满足它——测试通过不等于 AI 自以为正确，而是符合你定义的行为规格。

  

**拆完之后，有两种执行节奏——取决于 Task 之间有没有依赖：**

  

**节奏一：串行（有依赖 / 需要人工验收）**

  

Task1 → 验收 → commit → Task2 → 验收 → commit → ...

Task 之间存在依赖、方向不确定、改动影响大——必须每一步验收后再推进。代价是慢，好处是一旦发现方向错了，止损成本最小。

  

**节奏二：并发（完全独立）**

  

Task1 ──────→ 验收 ─┐

Task2 ──────→ 验收 ─┤→ 合并

Task3 ──────→ 验收 ─┘

多个 Task 接口清晰、互不依赖——交给并发子 Agent 同时跑，各自有验收标准，最后合并。

  

**判断标准**：「Task A 做错了，Task B 还能继续做吗？」能继续 → 并发；不能继续 → 串行。

  

**实践线索**：

  

文件处理功能拆成 4 个 Task，每个 Task 有明确的测试目标：

- Task1：实现 `detectFileMode`，7 个测试覆盖所有边界（单 MEDIA、多 MEDIA、tilde 路径、普通路径、无路径）

- Task2：实现并测试模式1（`handleOutboundFileMessage` mode1）

- Task3：实现并测试模式2（mode2）

- Task4：更新 `monitor.ts`，替换旧逻辑，原有测试全部通过

Task1–3 逻辑独立，可以并发交给三个子 Agent 同时执行；Task4 依赖前三个结果，必须在最后串行运行。这不是在「全串」和「全并」之间二选一，而是根据依赖关系灵活编排节奏。

  

**技巧六：Make Checkpoint——多 commit，给自己留后路**

AI 的改动有时超出预期范围，或者改着改着把原本好的逻辑覆盖掉。这类问题很难预防，但可以用 Git 来兜底。

  

**核心原则**：每完成一个可验证的小步骤，立刻 commit。不要攒到「功能完整了」再提交。

  

**实践模式**：

  

- 每个 Task 执行完、测试通过后 → commit  
    
- 设计文档定稿后 → commit  
    
- 重构前的稳定状态 → commit（这是重构的安全基线）  
    

这样即使 AI 在某一步把代码搞坏，**git diff** 立刻能看出问题，**git checkout** 一条命令回到上一个可工作状态。

  

**频繁 commit 的另一个好处**：commit 历史本身就是「AI 做了什么」的记录。出问题时，可以直接把相关 commit diff 发给 AI，让它定位是哪一步引入了问题。

  

**技巧七：Provide Evidence——遇到难题不要猜，让数据说话**

AI 在面对难以复现的 bug 时，往往倾向于「猜」——给出几个可能的原因，让你逐一排查。这种方式效率很低，而且方向容易错。

  

**正确的姿势**：明确告诉 AI，遇到无法分析定位的问题，不要猜，改为：

  

1. **AI 设计日志方案**：在关键路径插入带特征关键字的调试日志  
    
2. **人工触发测试**：在真实环境复现问题，收集日志  
    
3. **把日志发回给 AI**：AI 基于真实运行数据定位根因  
    

这个闭环把「AI 的代码分析能力」和「人的真实环境访问能力」结合起来，各自发挥优势。

  

例如：**CLAUDE.md** 里明确写着：「遇到难解决或者无法发现原因的问题时，可以增加带问题关键字的特殊日志，我会进行测试验证，将日志发回给你来协助你定位问题」

  

**关键原则**：凡是「看代码猜不出来」的问题，第一反应应该是「加日志，拿数据」，而不是让 AI 继续猜。

  

**技巧八：Minimal Changes——多方案中选改动面最小的**

评估多个可行方案时，除了「能不能实现」，还要问「哪个方案的改动面最小」。改动面越小，引入风险越低，Review 越容易。

  

例如：需求「服务端能动态下发长任务提示延迟配置，不重启生效」：

  

|   |   |
|---|---|
|方案|改动面|
|新增独立「拉配置」API|新接口 + 新调用时机 + 新错误处理|
|在 getUpdates 响应加可选 config 字段|扩展现有返回类型，利用已有 poll 循环|

选了后者。配置随每次 poll 自然返回，≤30s 内生效，不需要任何新接口，改动面极小。

  

**提问模板**：让 AI 给出方案时，加一条要求：「同时给出改动面最小的方案，并说明为什么它最小」。这能引导 AI 在正确性之外，也考虑工程代价。

  

**技巧九：Timely Refactor——认准重构时机，别无限打补丁**

AI 打补丁的速度很快，但这也意味着技术债可以堆得很快。每次加需求、修 bug，AI 都能给出一个「能跑」的方案，但如果模块已经复杂到一定程度，这种修法只会让情况越来越难收拾。

  

**识别重构时机**：不是「代码丑就重构」，而是出现了明确信号：

  

- AI 每次修完，又冒出规则之外的新 case  
    
- 描述问题越来越难，每次提 prompt 都要铺一大堆背景  
    
- 改一处动一处，改了又出新问题  
    

这时候与其继续让 AI 打补丁，不如主动叫停：退一步，重新整理这个模块的需求边界，做一次系统化重构。

  

重构时，不要直接让 AI「重构一下」——容易在中间状态把代码搞坏，或者改了接口破坏上层调用。正确方式是把重构拆成多个 Task，「对外接口不变」作为底线，每步可验证。

  

﻿**file-handle.ts** 的路径检测逻辑就经历了这个过程——积累了 4 个正则和复杂手工去重后，拆成 7 个 Task 系统化重构，最终 44 个测试全部通过，公开接口签名零改动，上层调用方无感知。

  

**核心判断**：AI Coding 的节奏越快，越需要人主动识别「该整理了」的时机。这个判断 AI 给不了你，只有你自己知道补丁什么时候已经补不动了。

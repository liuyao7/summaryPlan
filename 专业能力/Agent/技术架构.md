# AI Agent 主流技术架构

## 一、核心循环：ReAct 范式（Agent 的"心跳"）

几乎所有 Agent 都遵循同一套循环，**这套循环本身极其稳定，几乎不随产品变化**：

```
感知(Perceive) → 思考(Reason) → 行动(Act) → 观察(Observe) → 循环...
```

具体展开：

| 阶段 | 做什么 | 技术实现 |
|------|--------|---------|
| **感知** | 接收用户输入 + 检索相关记忆/上下文 | Gateway 消息接入 + 向量/全文检索 |
| **思考** | 大模型决定下一步：用工具？还是直接回复？ | LLM + System Prompt + Tool Description |
| **行动** | 执行工具调用（搜索/代码/浏览器/API） | Function Calling / Tool Use |
| **观察** | 把工具执行结果喂回大模型 | 结果序列化 → 拼入上下文 |
| **判断** | 任务完成则结束，否则回到"思考" | 模型自主决定，或设定最大循环次数 |

**关键设计原则**：新能力只在循环外部叠加（扩展工具、调整 System Prompt、外化状态到文件/数据库），**核心循环体本身不应该变成巨大的状态机**。模型负责推理，外部系统负责状态和边界。

## 二、四大基础设施

### 1. 记忆系统（Memory）

记忆是区分"初级 Agent"和"高级 Agent"的核心分水岭。采用分层设计：

| 记忆层 | 存储形式 | 生命周期 | 代表实现 |
|--------|---------|---------|---------|
| **工作记忆** | 当前对话滑动窗口 | 单次会话 | 所有 Agent |
| **短期记忆** | 最近N次对话摘要 | 跨会话（有限） | ChatGPT Conversation Summary |
| **长期记忆** | MEMORY.md / 向量库 / SQLite | 持久化 | Hermes 四层记忆、OpenClaw MEMORY.md |
| **程序性记忆** | Skill 文件（可复用的操作流程） | 持久化 | Hermes 闭环生成、OpenClaw SKILL.md |

**两种记忆实现路线**：
- **精简路线（ChatGPT）**：不用向量库，~33条关键偏好 + ~15条对话摘要，极简主义
- **全量路线（Hermes MemPalace）**：全存下来，FTS5 全文搜索检索，检索准确率 60% → 95%

**核心判断**：不应该让AI来决定什么值得记——AI判断不可信，不如全存下来，让检索来决定什么有用。

### 2. 工具调用（Tools / Function Calling）

让 Agent "长出手脚"：

> 你在工具调用层设计什么工具 = Agent 的能力边界

| 工具类型 | 举例 | 技术实现 |
|---------|------|---------|
| **搜索** | 网页搜索、知识库查询 | Web Search API / RAG + 向量检索 |
| **代码** | 执行 Python/Shell | 沙箱环境 / Docker 隔离 |
| **浏览器** | 打开网页、点击、填表 | Computer Use / Playwright / Browser-Use |
| **文件** | 读写本地文件 | 文件系统权限控制 |
| **API** | 调用外部服务 | MCP 协议标准化连接 |
| **通信** | 发邮件、飞书消息 | Webhook / SDK 集成 |

**关键趋势**：
- **MCP（Model Context Protocol）**：正在统一所有工具连接标准——一套协议对接数据库、API、文档，不再为每个工具写特定插件
- **Skills**：更高层的抽象——把"工具组合 + 领域知识 + 操作规范"打包成可复用能力包

### 3. 上下文管理（Context）

Token 窗口有限，核心策略：

| 策略 | 原理 | 应用 |
|------|------|------|
| **滑动窗口** | 保留最近 N 轮，丢弃旧内容 | 所有 Agent 基础能力 |
| **上下文压缩** | 用 LLM 对历史做摘要后注入 | 超阈值自动触发 |
| **按需加载** | Skills 只加载名称，正文用到了再调入 | Hermes：200个Skill 上下文成本几乎不变 |
| **外化状态** | 把进度写到文件，不依赖 AI 的"脑子" | feature-list.json + Git log 断点续跑 |

> 脑子会忘，文件不会。长任务应该把状态外化到文件系统。

### 4. 评估与监控（Evaluation / LLMOps）

Agent 运行过程是黑盒，需要完整的可观测性：

| 维度 | 工具/方法 |
|------|----------|
| **全链路追踪** | LangSmith / Langfuse 追踪每次思考-行动-观察 |
| **效果评估** | LLM-as-a-Judge（用另一个模型打分） |
| **成本监控** | Token 消耗追踪 + 模型降级策略 |
| **容错恢复** | 模型回退链（gpt-5.4 → k2.5 → qwen3.5 → ollama） |

> Prompt 是武器，评估是你的准心。评估比训练更重要。

## 三、两种协作模式

根据 Anthropic 的定义：

| | Workflow（工作流） | Agent（智能体） |
|------|------|------|
| **控制权** | 代码预先写死执行路径 | **LLM 动态决定下一步** |
| **适用场景** | 流程固定、可预测 | 需要灵活判断、探索性 |
| **代表** | Manus 实际运作方式 | Hermes / Devin |
| **优缺点** | 稳定可预期，但死板 | 灵活，但需要评估验证 |

> 现实中很多标着"Agent"的产品深入看更接近 Workflow，两者无高下之分。

## 四、多 Agent 架构（2026 标配）

单个 Agent 无法覆盖所有场景，多 Agent 协作成为主流：

**常见分工模式**：
```
规划Agent（拆任务）→ 执行Agent（干活）×N → 审查Agent（检查）→ 总结Agent（汇报）
```

**通信协议**：
- **A2A（Agent-to-Agent）**：Google 提出的 Agent 间协作协议标准
- **MessageBus / 事件总线**：代理商通过共享消息通道通信，Agent 代码和渠道完全解耦

## 六、Harness Engineering 五大组件

Mitchell Hashimoto 提出的 Agent 工程化核心框架：

1. **指令层（Instructions）**：System Prompt——Agent 的角色、目标、行为约束
2. **约束层（Constraints）**：安全边界——沙箱、权限、人工复核、审计日志
3. **反馈层（Feedback）**：评估闭环——任务完成质量检测、用户反馈采集
4. **记忆层（Memory）**：分层记忆——工作/短期/长期/程序性记忆
5. **编排层（Orchestration）**：执行控制——ReAct 循环、工具调度、子Agent管理

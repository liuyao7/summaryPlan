## 4.1 ER 建模

### 必须掌握

- **实体（Entity）**：现实世界中可区分的事物 → 一张表
- **属性（Attribute）**：实体的特征 → 列
- **关系（Relationship）**：实体之间的关联

| 关系类型 | 示例 | 实现方式 |
|----------|------|----------|
| 1:1（一对一） | 用户 ↔ 用户详情 | 外键 + UNIQUE 约束，或合并为一张表 |
| 1:N（一对多） | 部门 ↔ 员工 | 多方加外键 |
| M:N（多对多） | 学生 ↔ 课程 | 中间表（关联表），两列外键组成联合主键 |

- **ER 图绘制**：实体用矩形、属性用椭圆、关系用菱形。推荐工具：draw.io / dbdiagram.io
- **继承关系建模**：单表继承 / 类表继承 / 具体表继承，三种策略各自适用场景

## 4.2 范式与反范式

### 必须掌握

#### 什么时候满足范式
- 数据一致性要求高（金融、交易系统）
- 写入频繁、更新多
- 数据冗余会带来维护噩梦

#### 什么时候反范式
- **高频读取、低频写入**：JOIN 开销大时做冗余
- **统计/报表场景**：提前计算好汇总列，避免实时聚合
- **分库分表后**：跨库 JOIN 不可行，需要冗余字段避免跨库查询

#### 常见反范式手段
- **冗余列**：订单表存 `user_name`，避免 JOIN 用户表
- **预聚合**：帖子表加 `comment_count`，评论增删时同步更新
- **快照表**：定期生成不可变快照，供报表查询

## 4.3 数据类型选型

### 必须掌握

| 场景 | 推荐类型 | 避免 |
|------|---------|------|
| 主键/ID | BIGINT UNSIGNED AUTO_INCREMENT 或 CHAR(36) UUID | VARCHAR 主键 |
| 状态/枚举 | TINYINT + 注释 或 ENUM | VARCHAR |
| 金额 | DECIMAL(18,2) 或 BIGINT（分） | FLOAT / DOUBLE |
| 时间 | DATETIME(3) 或 TIMESTAMP | VARCHAR 存时间 |
| 长文本 | TEXT / MEDIUMTEXT | VARCHAR(65535) |
| JSON | JSON 类型（MySQL 5.7+） | TEXT 存 JSON 字符串 |
| 布尔 | TINYINT(1) | — |
| IP 地址 | INT UNSIGNED（INET_ATON / INET_NTOA） | VARCHAR(15) |
| 固定长度字符串 | CHAR(N) | VARCHAR（CHAR 效率更高） |
| 变长字符串 | VARCHAR(N) | CHAR（空间浪费） |

- **存储空间 = 查询性能的隐藏成本**：字段越小，每页能放更多行 → 缓存命中率高

## 4.4 分库分表策略

### 必须掌握

#### 垂直拆分（按业务模块）
```
原大库 → 用户库（user） + 订单库（order） + 商品库（product）
```
- 解决：单表字段过多、业务耦合
- 问题：原来 JOIN 就能查的跨模块数据 → 需要应用层聚合

#### 水平拆分（按数据行）
```
orders → orders_0, orders_1, ..., orders_15（16张表，按 user_id % 16）
```
- 分片键（Sharding Key）选择原则：
  - 查询条件中出现频率最高的字段
  - 数据分布均匀（避免热点）
  - 尽量不跨分片
- 常见分片算法：取模（%）、Hash、Range（按时间范围）、List（按地区）

#### 分表后的问题与对策

| 问题 | 对策 |
|------|------|
| 全局唯一 ID | 雪花算法（Snowflake）、号段模式（Leaf）、UUID7 |
| 跨分片查询 | 应用层聚合、中间件支持（ShardingSphere） |
| 跨分片排序/分页 | 从各分片取 Top N，在应用层归并排序（内存瓶颈） |
| 跨分片 JOIN | 避免：冗余字段、ER 分片（关联表放同一分片）、应用层 JOIN |
| 分布式事务 | Seata / TCC / 消息队列最终一致性（见第05模块） |
| 扩容/缩容 | 一致性 Hash、双写迁移 |

## 4.5 特殊场景建模

### 必须掌握

#### 树形结构
- **邻接表**（id + parent_id）— 简单但查子/孙需递归 CTE
- **路径枚举**（path: /1/3/7/）— 查祖先快，但移动节点成本高
- **嵌套集**（lft + rgt）— 查子树 O(1)，但插入成本高
- **闭包表** — 存所有祖先-后代关系，查询最快但空间开销大

#### 时序数据
- 按月/按天分表（如 `sensor_data_202605`）
- 列式存储考虑（ClickHouse、TimescaleDB）
- 降采样 + 过期策略

#### 日志/审计
- 不可变设计（Append Only，不 Update/Delete）
- 按时间分区、定期归档到冷存储

#### 多租户（SaaS）
- 每租户独立数据库（隔离最强、成本最高）
- 每租户独立 Schema（折中）
- 共享表 + tenant_id 列（成本低、隔离最弱）

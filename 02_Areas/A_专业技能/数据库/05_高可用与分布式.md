## 5.1 主从复制（Replication）

### 必须掌握

#### 复制原理（MySQL）

```
主库：binlog（二进制日志）记录所有变更
  ↓ (IO 线程读取)
从库：Relay Log（中继日志）→ SQL 线程回放
```

| 复制模式 | binlog 格式 | 优点 | 缺点 |
|----------|-------------|------|------|
| **STATEMENT** | SQL 语句 | 日志量小 | 部分函数（NOW()、UUID()）导致不一致 |
| **ROW** | 行变更数据 | 准确、可靠（MySQL 5.7+ 默认） | 日志量大 |
| **MIXED** | 混合 | 平衡 | 不直观 |

#### 复制类型

| 类型 | 说明 | 数据延迟 |
|------|------|----------|
| 异步复制 | 主库提交后不等待从库确认 | 可能丢失数据 |
| 半同步复制 | 至少一个从库收到 binlog 才返回成功 | 延迟较小 |
| 全同步复制（Group Replication） | 多数节点确认后才提交 | 延迟大但强一致 |

#### GTID（全局事务标识符）
- 每个事务有唯一 ID，简化主从切换和故障恢复
- `SHOW MASTER STATUS` / `SHOW SLAVE STATUS` 查看复制状态
- `Seconds_Behind_Master`：从库延迟秒数（不为 0 就要警惕）

## 5.2 读写分离

### 必须掌握

#### 架构模式
```
         ┌── 主库（写）──┐
App ─→ 路由层           复制
         └── 从库1 从库2（读）──┘
```

#### 实现方式
| 方式 | 工具 | 复杂度 |
|------|------|--------|
| 客户端路由 | 代码中判断读写 | 低 |
| 中间件代理 | MySQL Router / ProxySQL / MaxScale | 中 |
| ORM 集成 | 配置多数据源 | 低 |

#### 核心问题：主从延迟

| 场景 | 问题 | 解决方案 |
|------|------|----------|
| 写后立刻读 | 从库还没同步 | 写后读走主库 |
| 延迟较大 | 用户看到旧数据 | 关键业务强制走主库 |
| 主从切换 | 数据不一致 | GTID + 半同步复制降低风险 |

- **什么时候必须走主库**：刚写完 → 立刻读、分布式锁、乐观锁版本检查
- **什么时候可以从库读**：列表查询、历史数据、报表、对实时性要求不高的查询

## 5.3 分布式事务

### 必须掌握

| 方案 | 原理 | 一致性 | 性能 | 适用场景 |
|------|------|--------|------|----------|
| **2PC（XA）** | 协调者 → 参与者准备 → 全部就绪 → 提交 | 强一致 | 差 | 传统金融（较少用） |
| **TCC** | Try（预留）→ Confirm（确认）→ Cancel（取消） | 最终一致 | 中 | 资金类业务 |
| **Seata AT** | 自动生成回滚 SQL，一阶段提交 + 二阶段回滚 | 最终一致 | 中 | 微服务间分布式事务 |
| **Saga** | 本地事务 + 补偿事务链 | 最终一致 | 好 | 长事务、微服务编排 |
| **消息队列** | 本地事务 + 事务消息（RocketMQ） | 最终一致 | 好 | 异步解耦场景 |

#### 核心思想
- **刚性事务（强一致）**：2PC → 实现复杂、性能差 → 基本不用
- **柔性事务（最终一致）**：TCC / Saga / 消息队列 → 工业界主流

#### 关键设计原则
- 每个本地事务尽量短
- 补偿操作必须幂等
- 补偿操作不允许失败（需要重试 + 告警 + 人工介入）

### 学后任务

## 5.4 分片中间件

### 必须掌握

| 中间件 | 类型 | 特点 |
|--------|------|------|
| **ShardingSphere-Proxy** | 代理层 | 独立部署、多语言支持（像连普通 MySQL 一样连接） |
| **ShardingSphere-JDBC** | 客户端 SDK | 嵌入业务代码、性能高、Java 专用 |
| **Vitess** | 代理层 | YouTube 出品、面向 MySQL、云原生 |
| **MyCat / DBLE** | 代理层 | 国产、文档中文 |

#### ShardingSphere 核心概念
- **分片键（Sharding Key）**：决定数据落在哪个分片
- **分片算法**：INLINE（取模）、HASH_MOD、RANGE、INTERVAL（日期）
- **分片策略**：标准策略（= / IN）、复合策略（多键）、Hint 策略（强制路由）
- **绑定表**：关联表按相同分片键分片，避免 JOIN 跨库
- **广播表**：每个分片都有完整副本的小表（字典表、配置表）

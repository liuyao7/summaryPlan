## 3.1 事务隔离级别

### 必须掌握

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现方式 |
|----------|------|-----------|------|----------|
| READ UNCOMMITTED | ✓ | ✓ | ✓ | 不加锁，几乎不用 |
| READ COMMITTED | ✗ | ✓ | ✓ | 每次读最新已提交版本（默认 RC：PostgreSQL、Oracle） |
| REPEATABLE READ | ✗ | ✗ | ✓（InnoDB 用间隙锁消除） | 事务内读同一快照（默认 RR：MySQL InnoDB） |
| SERIALIZABLE | ✗ | ✗ | ✗ | 读加共享锁，写加排他锁，串行执行 |

- **脏读**：读到其他事务未提交的数据
- **不可重复读**：同一事务内两次读同一行，结果不同（被其他事务 UPDATE 了）
- **幻读**：同一事务内两次查同一范围，记录数不同（被其他事务 INSERT/DELETE 了）

- **如何设置**：`SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;`

> 1. 在 READ UNCOMMITTED 下演示脏读（Session A 更新未提交，Session B 能读到）
> 2. 在 READ COMMITTED 下演示不可重复读（Session A 两次读之间 Session B 提交了修改）

## 3.2 锁机制

### 必须掌握

#### 锁的类型

| 锁 | 粒度 | 说明 |
|----|------|------|
| 全局锁 | 库 | `FLUSH TABLES WITH READ LOCK`，全库只读（备份用） |
| 表锁 | 表 | `LOCK TABLES ... READ/WRITE`，MyISAM 默认 |
| 行锁 | 行 | InnoDB 默认，通过索引实现（没索引 → 锁全表！） |
| 元数据锁（MDL） | 表 | DML 时自动加，防止 DDL 和 DML 冲突 |

#### InnoDB 行锁分类

| 锁 | 说明 |
|----|------|
| **共享锁（S Lock）** | SELECT ... LOCK IN SHARE MODE，允许其他事务读，不允许写 |
| **排他锁（X Lock）** | SELECT ... FOR UPDATE / UPDATE / DELETE，不允许其他事务读写 |
| **意向锁（IS/IX）** | 表级锁，表示"我打算加行锁"，用于表锁和行锁之间的协调 |
| **记录锁（Record Lock）** | 锁定单个索引记录 |
| **间隙锁（Gap Lock）** | 锁定索引记录之间的间隙，防止幻读（RR 级别下生效） |
| **临键锁（Next-Key Lock）** | = Record Lock + Gap Lock，InnoDB 默认行锁形式 |
| **插入意向锁** | INSERT 前加的 Gap 锁，不互斥（允许并发插入不同位置） |

#### 死锁
- **条件**：互斥 + 持有等 + 不可剥夺 + 循环等待
- **排查**：`SHOW ENGINE INNODB STATUS` → LATEST DETECTED DEADLOCK 段
- **预防**：按相同顺序访问资源、缩短事务、加锁粒度一致

## 3.3 MVCC（多版本并发控制）

### 必须掌握

#### 核心概念
- **目的**：读不阻塞写，写不阻塞读，提高并发性能
- **实现方式**：每行数据有多个版本，事务根据版本号可见性规则选择合适的版本

#### MySQL InnoDB 实现

| 隐藏列 | 说明 |
|--------|------|
| `DB_TRX_ID` | 最近修改该行的事务ID（6字节） |
| `DB_ROLL_PTR` | 指向 Undo Log 中旧版本的指针（回滚指针，7字节） |
| `DB_ROW_ID` | 行ID（若无主键则用此作为聚簇索引键，6字节） |

- **ReadView（快照）**：事务开始时生成，决定哪些版本可见
- **可见性规则**：
  - 版本 trx_id < ReadView 最小活跃事务 → 可见（已提交）
  - 版本 trx_id > ReadView 最大事务 → 不可见（未开始）
  - 版本 trx_id 在活跃列表中 → 不可见（未提交）

#### PostgreSQL 实现
- 基于 xmin / xmax 元组可见性，配合 VACUUM 清理死元组
- 无 Undo Log，旧版本存在表本身（需要定期 VACUUM）

## 3.4 乐观锁 vs 悲观锁

### 必须掌握

| | 悲观锁 | 乐观锁 |
|------|--------|--------|
| 思路 | 假定冲突必然发生，先加锁 | 假定冲突很少发生，提交时检查 |
| 实现 | SELECT ... FOR UPDATE | 版本号 / 时间戳 CAS |
| SQL 示例 | `SELECT stock FROM product WHERE id=1 FOR UPDATE;` | `UPDATE product SET stock=stock-1, version=version+1 WHERE id=1 AND version=5;` |
| 适用 | 冲突率高、短事务 | 冲突率低、读多写少 |
| 风险 | 死锁、锁等待超时 | ABA 问题、重试循环 |

- **理解 version 字段**：每次更新 version+1，WHERE 条件带 version → 确保基于最新版本更新
- **ABA 问题思考**：version 单调递增可避免，但如果用 timestamp 则可能出问题

>    - **悲观锁版本**：SELECT FOR UPDATE → 检查库存 → UPDATE

> 4. 压测：模拟 1000 并发扣减，对比两种方案的正确率、TPS、平均等待时间
